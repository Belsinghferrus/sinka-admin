3. AUTHENTICATION FLOW: BEFORE AND AFTER
--------------------------------------------------------------------------------
Before:
  - Frontend called customer endpoints: POST /api/auth/firebase-login and
    GET /api/auth/me.
  - No clear differentiation between customer and administrator authentication
    routes.
  - Potential risk of customer accounts obtaining sessions without admin-specific
    backend verification.

After:
  - Login Flow:
      1. Administrator clicks "Sign In with Google (Administrator)".
      2. Firebase Client SDK prompts user and returns Google credential.
      3. Frontend extracts Firebase ID Token (user.getIdToken()).
      4. Frontend sends POST /api/admin/auth/login with { idToken: "<FIREBASE_ID_TOKEN>" }.
      5. Backend verifies token with Firebase Admin SDK, looks up user in MongoDB.
      6. If user.role !== 'admin', backend immediately responds with 403 FORBIDDEN.
      7. Frontend only marks user authenticated when backend responds 200 OK with
         role: 'admin'.
      8. Session token is stored in memory and localStorage for API client interceptor.
  - Session Restoration:
      1. On page refresh, AuthProvider detects stored Firebase token / Firebase session.
      2. Calls GET /api/admin/auth/me with Authorization: Bearer <token>.
      3. If valid and admin, profile is restored.
      4. If 401 or 403, session is destroyed and user is redirected to /login.
  - Logout Flow:
      1. Calls authService.logout().
      2. Clears localStorage token, signs out of Firebase Client SDK.
      3. State resets to unauthenticated; ProtectedRoute bounces to /login.


4. API ENDPOINTS INTEGRATED
--------------------------------------------------------------------------------
All endpoints are prefixed with the baseURL (e.g. http://localhost:5001/api).

A. Authentication Endpoints:
  1. POST /api/admin/auth/login
     - Request Header: Content-Type: application/json
     - Request Body: { "idToken": "<Firebase ID Token>" }
     - Response (200):
       {
         "success": true,
         "data": {
           "user": {
             "id": "...",
             "email": "...",
             "role": "admin",
             "displayName": "..."
           },
           "token": "<Firebase ID Token>"
         }
       }
     - Failure (401/403):
       { "success": false, "error": { "code": "FORBIDDEN", "message": "Access denied. Administrator privileges required." } }

  2. GET /api/admin/auth/me
     - Request Header: Authorization: Bearer <Firebase ID Token>
     - Response (200):
       {
         "success": true,
         "data": {
           "user": { "id": "...", "email": "...", "role": "admin", "displayName": "..." }
         }
       }

B. Promotional Offer Endpoints:
  All offer endpoints require: Authorization: Bearer <Firebase ID Token>

  1. GET /api/admin/offers
     - Query Parameters: ?page=1&limit=20&status=all (or 'active', 'inactive')
     - Response (200):
       {
         "success": true,
         "data": { "offers": [...] },
         "meta": { "total": 1, "page": 1, "limit": 20, "totalPages": 1 }
       }

  2. GET /api/admin/offers/:id
     - Param: 24-char hex ObjectId
     - Response (200):
       { "success": true, "data": { "offer": { ... } } }

  3. POST /api/admin/offers
     - Request Body:
       {
         "title": "Spring Living Room Sale",
         "description": "Up to 40% off handcrafted sofas and teak tables.",
         "imageUrl": "https://images.unsplash.com/photo-...",
         "ctaLabel": "Shop Now",
         "ctaUrl": "/products?category=living",
         "offerDetails": "Valid through May 15.",
         "priority": 10,
         "startDate": "2026-05-01T00:00:00.000Z",
         "endDate": "2026-05-31T23:59:59.000Z",
         "isActive": true
       }
     - Response (201):
       { "success": true, "data": { "offer": { ... } } }

  4. PUT /api/admin/offers/:id
     - Request Body: Full replacement fields matching create schema
     - Response (200):
       { "success": true, "data": { "offer": { ... } } }

  5. PATCH /api/admin/offers/:id
     - Request Body: Partial fields to update
     - Response (200):
       { "success": true, "data": { "offer": { ... } } }

  6. PATCH /api/admin/offers/:id/status
     - Request Body: { "isActive": true | false }
     - Response (200):
       { "success": true, "data": { "offer": { ... } } }

  7. DELETE /api/admin/offers/:id
     - Response (200):
       { "success": true, "data": { "id": "...", "deleted": true } }

  8. GET /api/admin/offers/active
     - Response (200):
       { "success": true, "data": { ... winning offer or null ... } }


5. ENVIRONMENT VARIABLES REQUIRED
--------------------------------------------------------------------------------
The admin frontend requires the following environment variables (stored in .env
or configured via deployment provider). No secret keys or private service accounts
are placed in client code:

  Variable Name                      Purpose / Description
  ---------------------------------  -------------------------------------------
  VITE_API_BASE_URL                  Base URL for backend REST API
                                     (e.g., http://localhost:5001/api)
  VITE_FIREBASE_API_KEY              Firebase Web Client public API key
  VITE_FIREBASE_AUTH_DOMAIN          Firebase project auth domain
  VITE_FIREBASE_PROJECT_ID           Firebase project ID
  VITE_FIREBASE_STORAGE_BUCKET       Firebase storage bucket
  VITE_FIREBASE_MESSAGING_SENDER_ID  Firebase Cloud Messaging sender ID
  VITE_FIREBASE_APP_ID               Firebase Web App client ID

Note: Firebase Admin SDK service account credentials (private keys) remain strictly
on the backend and are NEVER exposed to the frontend browser application.


6. CORS FINDINGS & RECOMMENDATION
--------------------------------------------------------------------------------
- Inspection of Sinka-backend/config/env.js and Sinka-backend/.env revealed:
    CORS_ORIGIN=http://localhost:5173
- The customer storefront runs on port 5173 (http://localhost:5173).
- The admin panel runs on port 5174 (http://localhost:5174).
- Impact: When the admin frontend in a live browser sends cross-origin fetch/axios
  requests to http://localhost:5001/api, the backend CORS middleware will reject
  requests originating from http://localhost:5174 because 5174 is not currently
  in CORS_ORIGIN.
- Scope Rule Adherence: Per Phase 3 rules ("Do not modify backend CORS settings
  unless a real integration issue requires it. If a backend change is necessary,
  document it separately and request approval before expanding the scope"),
  Sinka-backend was NOT modified.
- Recommendation for User Approval:
  Update Sinka-backend/.env:
    CORS_ORIGIN=http://localhost:5173,http://localhost:5174
  (Or alternatively configure a dev proxy in sinka-admin/vite.config.js).
