3. LOGIN AND SESSION FLOW
--------------------------------------------------------------------------------
A. Administrator Login:
  1. Administrator visits http://localhost:5174/login.
  2. Enters email (e.g., sinkahomeliving@gmail.com) and password.
  3. Client validates: non-empty, valid email format, non-empty password.
  4. Form dispatches authService.login({ email, password }).
  5. Axios sends POST /api/admin/auth/login with body:
       { "email": "sinkahomeliving@gmail.com", "password": "..." }
  6. Backend verifies credentials against Admin collection in MongoDB with bcrypt.
  7. Backend issues signed 24-hour HS256 JWT:
       { "adminId": "...", "email": "...", "role": "admin", "exp": <now + 24h> }
  8. Frontend validates response.data.success and user.role === 'admin'.
  9. Token is stored via setAuthToken(token).
 10. User state is updated in AuthProvider; router redirects to intended route
     or /dashboard.

B. Session Hydration on Page Reload:
  1. On reload, AuthProvider checks if stored token exists via hasStoredSession().
  2. If none, sets isLoading(false); ProtectedRoute redirects to /login.
  3. If token exists, performs advisory expiration check (exp * 1000 <= Date.now()).
     - If expired locally, token is purged immediately without network overhead.
  4. Sends GET /api/admin/auth/me with header:
       Authorization: Bearer <admin_jwt>
  5. Backend cryptographically validates token against JWT_SECRET and checks MongoDB
     to verify account exists and isActive === true.
  6. If 200 OK: session is restored, user profile set in state.
  7. If 401 / 403: token is cleared, user state set to null, redirected to /login.

C. Administrator Logout:
  1. User clicks "Sign Out" in Header or Sidebar.
  2. Frontend dispatches authService.logout().
  3. Sends POST /api/admin/auth/logout with Bearer token (non-blocking).
  4. Token is purged from in-memory cache and localStorage.
  5. User state is set to null; ProtectedRoute redirects to /login.

5. TOKEN STORAGE STRATEGY AND TRADE-OFFS
--------------------------------------------------------------------------------
Strategy Chosen:
  Hybrid Dual-Tier Storage (In-Memory + Web Storage):
  - Primary access tier: In-memory JavaScript variable (`inMemoryToken`).
    All outgoing Axios requests read directly from this variable in the interceptor,
    ensuring zero DOM/storage I/O overhead per HTTP request.
  - Secondary persistence tier: `window.localStorage` under key `sinka_admin_token`.
    Enables administrator sessions to survive browser tab refreshes across the
    24-hour token validity window.

Security Trade-Off Analysis:
  - Advantage over Cookie-Only in SPA:
    Avoids CSRF (Cross-Site Request Forgery) vulnerabilities because browsers do
    not automatically attach Authorization: Bearer headers on cross-site requests.
  - Advantage over In-Memory-Only:
    In-memory-only storage would force administrators to re-authenticate on every
    single page refresh, drastically degrading back-office usability.
  - Trade-off (XSS Consideration):
    Any JavaScript executing on the page can theoretically access localStorage.
    Mitigations implemented:
    1. Zero third-party scripts or CDNs loaded in index.html.
    2. Strict React JSX escaping prevents DOM injection.
    3. Strict backend Helmet CSP headers deployed on backend API responses.
    4. 24-hour finite lifetime strictly enforced by backend cryptographic verification.

7. ROUTE-GUARD BEHAVIOR
--------------------------------------------------------------------------------
The ProtectedRoute component guards all internal back-office routes:
  1. Initialization check: If isLoading === true, displays centered
     LoadingIndicator ("Verifying administrator authorization..."). No protected
     layout or sensitive data is rendered.
  2. Authentication check: If !isAuthenticated or !user, redirects immediately
     to /login via <Navigate replace />, preserving the attempted destination in
     router state (location.state.from) for post-login return.
  3. Role enforcement: If user.role !== 'admin', triggers logout and redirects
     to /login with access denied error.
  4. Verification: Tested via automated browser subagent; direct navigation to
     http://localhost:5174/offers immediately bounces to http://localhost:5174/login.
