1. EXECUTIVE SUMMARY & ROOT CAUSE INVESTIGATION
--------------------------------------------------------------------------------
The admin login screen displayed the error:
"Authentication Failed — Too many requests from this IP address. Please try again later."

A thorough audit of both the backend Express architecture and the frontend login
flow revealed the exact root cause and several interrelated rate-limiting flaws:

A. The Exact Triggering Middleware:
   - The error was generated by the GLOBAL API Rate Limiter in `Sinka-backend/app.js`
     (`limiter` mounted at line 86 via `app.use(limiter)`).
   - Its exact handler response:
     {
       "statusCode": 429,
       "code": "RATE_LIMIT_EXCEEDED",
       "message": "Too many requests from this IP address. Please try again later."
     }
   - The dedicated admin login rate limiter in `routes/admin/auth.routes.js`
     (`adminAuthRateLimiter`) produces a different error message:
     "Too many admin authentication attempts. Please try again after 15 minutes."
     It was NOT `adminAuthRateLimiter` that generated the error.

B. Rate Limit Overlap & Quota Starvation:
   - The global rate limiter in `app.js` enveloped all incoming requests under `/api/*`
     with a hard ceiling of `RATE_LIMIT_MAX = 100` requests per 15-minute window.
   - It only exempted `/health` and `/api/health`.
   - On `localhost` / `127.0.0.1` (which is shared by the admin dashboard on :5174,
     the storefront on :5173, and automated testing), normal browsing activity
     (fetching products, banners, offers, session checks, and Vite HMR updates)
     rapidly accumulated 100 requests.
   - Once the global threshold was crossed on `127.0.0.1`, the global limiter
     intercepted all subsequent traffic, including `POST /api/admin/auth/login`,
     locking administrators out before credentials could even be evaluated.

C. Flaws in the Dedicated Brute-Force Rate Limiter:
   - `adminAuthRateLimiter` had `skipSuccessfulRequests` set to `false` (default).
   - Consequently, successful logins were being penalized and counted against the
     brute-force limit.
   - Industry-standard brute-force defense requires `skipSuccessfulRequests: true`
     so that legitimate administrators with correct credentials can log in freely,
     while failed password guessing attempts are strictly penalized and blocked.

D. Absence of Reverse Proxy Trust Configuration:
   - Express had no `trust proxy` setting configured in `app.js`.
   - In production behind a reverse proxy (e.g. AWS ALB, Cloudflare, Nginx, Render),
     all incoming requests would share the reverse proxy's IP address. A single user's
     high activity would lock out all administrators globally.

E. Frontend Concurrency & In-Flight Invariants:
   - In `sinka-admin/src/pages/auth/LoginPage.jsx`, `handleSubmit` lacked an in-flight
     guard (`if (isSubmitting) return;`).
   - Rapid Enter keypresses or double-clicking could trigger duplicate authentication
     POST requests in parallel before React state disabled the submit button.
   - Form inputs were not disabled during submission.


2. ARCHITECTURAL REMEDIATION & CHANGES MADE
--------------------------------------------------------------------------------
A. Backend Changes (Sinka-backend):
   1. `config/env.js`:
      - Differentiated `RATE_LIMIT_MAX` by environment:
        * Development: 2,000 requests per 15 min window (prevents local dev lockout).
        * Test: 10,000 requests.
        * Production: 300 requests per 15 min window.
      - Introduced `ADMIN_LOGIN_RATE_LIMIT_MAX`:
        * Development: 50 failed attempts per 15 min window.
        * Production: 10 failed attempts per 15 min window.
      - Introduced `TRUST_PROXY` configuration with secure defaults.
   2. `.env`:
      - Set `RATE_LIMIT_MAX=2000` and `ADMIN_LOGIN_RATE_LIMIT_MAX=50` for local dev.
   3. `app.js`:
      - Configured `app.set('trust proxy', ...)` to securely handle reverse proxies:
        * Uses `env.TRUST_PROXY` if specified.
        * Defaults to `1` hop in production.
        * Defaults to `'loopback'` in development.
      - Updated global rate limiter `skip` function:
        * Skips `/health` and `/api/health`.
        * Skips dedicated auth endpoints (`/auth/login`, `/auth/firebase-login`)
          so general API browsing traffic cannot starve login attempts.
      - Emits standard `draft-8` headers and explicit `Retry-After` response header.
   4. `routes/admin/auth.routes.js`:
      - Configured `adminAuthRateLimiter` with `skipSuccessfulRequests: true`:
        * Successful admin logins do not increment the penalty counter.
        * Only failed attempts (invalid credentials, 401s) increment the counter.
      - Configured limit dynamically via `env.ADMIN_LOGIN_RATE_LIMIT_MAX`.
      - Emits standard `draft-8` headers and `Retry-After` header on 429.
   5. `tests/admin.test.js`:
      - Added test verifying successful admin logins succeed and are not blocked
        by global rate limiting.

B. Admin Frontend Changes (sinka-admin):
   1. `src/pages/auth/LoginPage.jsx`:
      - Added immediate in-flight guard: `if (isSubmitting) return;` at the start
        of `handleSubmit`.
      - Disabled email input, password input, and password visibility toggle
        while `isSubmitting` is true.
      - Specialized error feedback for HTTP 429 displaying Retry-After countdowns.
   2. `src/lib/api.js`:
      - Response interceptor parses `Retry-After` header on HTTP 429 responses.
      - Formats friendly countdown guidance:
        "Too many requests. Please wait X seconds before trying again."
   3. `tests/auth.test.js`:
      - Added unit test suite (7 tests) verifying client-side validation, JWT storage,
        role enforcement, HTTP 429 Retry-After parsing, and logout token purging.
